## 1. 背景与问题定义

### 1.1 现状

四合院的知识结构很好讲：中轴对称、坐北朝南、内外有别。但它有一个天然的传播难点——**名词多、形制近、看图能懂、合上书就忘**。

已有项目 [四合院布局图解](https://hh200606.github.io/siheyuan/) 解决了「院子怎么摆」：等轴测图 + 逐间点开 + 拖动旋转。上线后暴露了一个明显缺口：

> 用户能顺着图解点完 8 个房间，但让他关掉页面、只看一张窗棂特写，他说不出这是「步步锦」还是「龟背锦」。

也就是说，**理解（comprehension）有了，检索（retrieval）没有**。而真正的「学会」，恰恰发生在检索这一层。

### 1.2 问题陈述

> 想了解四合院的人，缺少一个**低成本、可重复、有反馈**的方式，来检验自己是否真的能分辨这些构件；而现有内容形态（长图、文章、纪录片）只提供输入，不提供检验。

拆成三个可验证的子问题：

| 编号 | 子问题 | 观察证据（当前） |
| :--- | :--- | :--- |
| P1 | 形制相近的构件，读者分不清 | 图解项目里「门墩」「窗棂」点击最多，但页面停留时间短，说明看了没记住 |
| P2 | 长内容没有「完成感」，读一半就走 | 图解是单向浏览，没有目标、没有终点、没有可炫耀的结果 |
| P3 | 学到的知识无处校验，错了也没人纠正 | 现有内容不设题、不给反馈、不解释错在哪 |

### 1.3 为什么是现在

1. 图解项目已经沉淀了**可靠的内容与美术资产**（三类形制、11 类构件的文案与画法），做一个测验型产品的边际成本低；
2. 网页版零依赖、无构建、可离线，**分发成本接近零**（一个链接）；
3. 小红书/朋友圈这类平台对「小而美的互动」有天然传播性，证书是现成的分享钩子。

### 1.4 备选方案与取舍

| 方案 | 优点 | 缺点 | 结论 |
| :--- | :--- | :--- | :--- |
| 做成题库文章（图文+答案） | 成本最低 | 无交互、无反馈、看完即走 | 否 |
| 做成建筑史课程（章节+测验） | 体系完整 | 太重，完课率低 | 否（作为远期） |
| 做成 AR 摄像头识构件 | 最有想象力 | 依赖真实照片与模型，一期做不出可信识别 | 否（列入 V2 探索） |
| **识图闯关（本题）** | 交互轻、反馈即时、可分享 | 题库容量有限 | **是** |

## 2. 目标与非目标

### 2.1 目标（按优先级）

| 编号 | 目标 | 衡量方式 |
| :--- | :--- | :--- |
| G1 | 让用户在 3 分钟内完成一次「我被考到了」的完整体验 | 从进入到看到结算的比例 ≥ 55% |
| G2 | 让「答错」变成学习时刻，而不是挫败 | 看过科普弹窗的用户，同题二次正确率 ≥ 70% |
| G3 | 产出一个用户愿意保存/分享的成果物 | 证书保存率 ≥ 15%；分享链接点击 ≥ 8% |
| G4 | 建立可持续扩题的内容生产规范 | 新增一个形制 ≤ 30 分钟（含文案与美术） |

### 2.2 非目标（明确不做）

| 非目标 | 理由 |
| :--- | :--- |
| 账号体系、云端存档 | 单机体验足够，引入账号会显著抬高使用门槛与隐私成本 |
| 排行榜 / 多人对战 | 用户规模不足以支撑榜单单有效；且会破坏「学习」而非「竞技」的定位 |
| 真实照片识别（一期） | 照片受光线、遮挡影响，误判会直接伤害可信度；V2 再评估 |
| 付费 / 广告 | 项目定位是开源作品集与公共知识产品 |
| 覆盖全部古建构件 | 一期只做「四合院」这一个场景，做深不做广 |

## 3. 用户与场景

### 3.1 目标用户

| 画像 | 特征 | 关键需求 | 触发场景 |
| :--- | :--- | :--- | :--- |
| **A. 古建爱好者**（核心） | 25–40 岁，看过纪录片/逛过胡同，知道「垂花门」但说不清门墩的等级 | 验证自己的眼力；收集冷知识 | 刷到分享链接、周末逛完胡同回家复盘 |
| **B. 建筑/设计学生** | 需要记构件名词应对课程与快题 | 快速自测、记住区分点 | 考前复习、做作业卡壳时 |
| **C. 文旅游客** | 刚逛完四合院景区，兴致最高 | 3 分钟轻体验、有 souvenir | 景区休息时、回酒店路上（手机） |
| **D. 教师/讲解员** | 需要课堂互动素材 | 可投屏、可离线、无广告 | 备课、现场讲解 |

### 3.2 关键用户旅程（JTBD）

> 当我**刚看完一座四合院**（或刚刷到一条相关内容）时，我想**用几分钟确认自己真的认得出这些构件**，这样我**才能把这次见闻讲给别人听**。

失败路径（必须避免）：
- 打开后看不懂要干什么（→ 需要 3 行以内的规则说明）；
- 连错两题后不知道该学什么（→ 每题答错必须给出「怎么区分」）；
- 玩到一半被打断（→ 进度可恢复，见 FR-9）；
- 玩完没有结果带走（→ 证书 + 分数）。

## 4. 成功指标

### 4.1 指标体系

| 层级 | 指标 | 定义 | 一期目标 | 当前 |
| :--- | :--- | :--- | :--- | :--- |
| **北极星** | 五关完成率（CR） | 完成第 5 关结算的人数 / 开始第 1 关的人数 | ≥ 40% | 未埋点 |
| 输入 | 首次会话开始率 | 点击开始 / 打开页面 | ≥ 70% | 未埋点 |
| 输入 | 单局时长中位数 | 从开始到结算 | 180–360 秒 | 未埋点 |
| 输入 | 平均正确率 | 答对题数 / 总题数 | 60–80% | 未埋点 |
| 输入 | 科普触达率 | 触发过至少一次错误反馈的比例 | 40–65% | 未埋点 |
| 输出 | 证书保存率 | 保存证书 / 完成五关 | ≥ 15% | 未埋点 |
| 输出 | 分享链接打开率（估） | 带 `?lv=` / `?end=` 参数的会话占比 | ≥ 8% | 未埋点 |
| 护栏 | 首屏可用时间 | LCP / 可交互 | ≤ 1.0s（4G） | 待测 |
| 护栏 | 中途放弃率（第 2–4 关） | 关间流失 | ≤ 25% | 未埋点 |
| 护栏 | 误判投诉 | 「这题答案不对」类反馈 | ≤ 1% 局数 | 0（暂无上报） |

> ⚠️ **诚实说明**：一期上线时**没有任何埋点**，上面目标值是待验证的产品假设，不是既有数据。第 13 节给出最小埋点方案与口径。

### 4.2 指标设计原则

1. **不看总访问量**，只看「完成率」与「正确率区间」——访问量高但没人玩完，说明内容或引导有问题；
2. **正确率不是越高越好**：> 90% 说明题目太水，< 40% 说明提示不足；
3. 护栏指标优先于增长指标：一旦首屏卡顿或答案有争议，先修体验再谈传播。

## 6. 功能需求

### 6.1 关卡与题库

| ID | 需求 | 优先级 | 验收标准 |
| :--- | :--- | :--- | :--- |
| FR-1.1 | 五关结构：窗棂 → 门墩 → 砖雕 → 院门 → 综合 | P0 | 关卡顺序与配置在内容层可改，不改渲染代码即可换关卡 |

**内容规范（新增形制的准入条件）**

1. 能在**单一局部图**里被辨认（不依赖环境、不依赖文字提示）；
2. 有**明确的形制差异**可与同类另三者区分（否则玩家只能猜）；
3. 科普文案必须写清三件事：一句话定位 / 与近亲的区别 / 文化含义或典故；
4. 美术需通过「四形制盲测」：随机给 10 人看，正确率 ≥ 70%。

## 8. 交互与状态

### 8.1 状态机

```
title ─开始→ playing
playing ─答对/答错→ feedback ─继续→ playing
playing ─题目答完→ levelClear ─下一关→ playing
playing ─生命耗尽 / 超时→ levelFailed ─重玩→ playing
最后一关通关 → finished（评级 + 证书）
```

### 8.2 关键流程与边界

| 场景 | 期望行为 |
| :--- | :--- |
| 连续快速点击选项 | 只接受第一次（答题瞬间进入 feedback 并禁用选项） |
| 弹窗打开时按数字键 | 不产生任何作答 |
| 切到后台标签页 | 计时暂停（避免「回来就超时」） |
| 窗口缩放 / 旋转 | 画布重绘不模糊，HUD 不换行错位 |
| 刷新页面 | 一期回到首页（FR-7.1 未实现，已知缺口） |
| 极端慢机 | 逻辑按固定上限 dt 推进，不出现「跳关」 |

### 8.3 文案规范

- 界面文案统一**中文书面语**，避免网络用语；
- 面向用户的称呼用「你」，不用「您」（降低距离感）；
- 科普文案**不写「正确答案是……」**，直接讲形制特征（弹窗标题已给答案）。

## 9. 内容与美术规范

### 9.1 词条结构（每个形制必须三件套）

| 字段 | 说明 | 示例 |
| :--- | :--- | :--- |
| `name` | 规范名称，≤ 6 字 | 抱鼓石 |
| `note` | 25–60 字，含「特征 + 区分点 + 文化含义」 | 形如圆鼓，鼓面雕纹，两侧有卷草。俗话说「门前抱鼓，非富即贵」。 |
| `art` | 一个可单图辨认的特征构图 | 圆鼓 + 卷草 + 石基座 |

### 9.2 美术规范

| 项 | 规范 |
| :--- | :--- |
| 逻辑画布 | 600×400，等比缩放，禁止非等比拉伸 |
| 调色板 | 宣纸 `#f3ead8` / 墨 `#262220` / 朱砂 `#9e3a2e` / 青瓦 `#4a607e` / 砖 `#968e84` |
| 线宽 | 主体 ≥ 4px（逻辑像素），保证缩到 360px 宽仍可辨 |
| 禁止 | 使用任何第三方图片素材（版权与一致性） |
| 验收 | 四形制对照图人工核对 + 盲测 ≥ 70% |

### 9.3 准确性

- 形制描述以公开建筑史资料为据，**不写未经验证的细节**；
- 涉及尺寸、等级排序时标注「示意」；
- 建立**勘误入口**（GitHub Issue 模板），任何用户可提交纠正。

## 10. 技术方案概要

| 层 | Web | 桌面 |
| :--- | :--- | :--- |
| 内容 | `docs/js/content.js` | `siheyuan_vision/questions.py` |
| 逻辑 | `docs/js/engine.js`（纯函数状态机） | `siheyuan_vision/game.py`（纯逻辑） |
| 渲染 | `docs/js/art.js` + Canvas 2D | `siheyuan_vision/art.py` + pygame.draw |
| 交互 | `docs/js/app.js`（DOM + 事件） | `siheyuan_vision/ui.py` |
| 测试 | `node --test tests/web-engine.test.js`（11 项） | `python -m unittest`（13 项）+ `tools/smoke.py` |
| 发布 | GitHub Pages（`/docs`） | 源码 + `run.py` |

**架构原则**：逻辑层不碰渲染，因此规则可在无头环境被完整测试；内容层与渲染层解耦，新增形制不需要改绘制代码。

**已知技术债**：规则在两种语言里各实现一份（JS/Python），修改需双端同步。缓解方案见第 17 节。

- 一期**不接入**任何第三方脚本（保持零依赖与可离线）。

## 12. 风险与对策

| 风险 | 影响 | 概率 | 对策 |
| :--- | :--- | :--- | :--- |
| **内容准确性被质疑** | 高（伤可信度） | 中 | 引用来源标注、勘误 Issue 模板、邀请建筑史背景的人审校 |
| **形制辨识度不足（玩家只能猜）** | 高（伤体验） | 中 | 四形制盲测 ≥ 70%；不达标就换构图 |
| 难度失衡（正确率 > 90% 或 < 40%） | 中 | 中 | 埋点后按题库逐题校准；提供「再练一题」 |
| 双端规则漂移 | 中 | 高 | 两端共用一套「数值契约」测试；或合并为单端 |
| 依赖 GitHub Pages 可用性 | 低 | 低 | 纯静态可镜像；README 提供本地打开方式 |
| 被当成「考据严谨的学术产品」 | 中 | 中 | 全站标注「示意图」，定位为科普互动 |
| 移动端性能 | 低 | 低 | 单画布、无阴影滤镜、DPR 上限 2.5 |
